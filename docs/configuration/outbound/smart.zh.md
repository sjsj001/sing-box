### 结构

```json
{
  "type": "smart",
  "tag": "smart",

  "alpha": 0.7,
  "groups": [
    {
      "tag": "hk",
      "outbounds": ["hk-1", "hk-2"],
      "select": "first"
    },
    {
      "tag": "jp",
      "outbounds": ["jp-1"],
      "select": "fastest",
      "bonus": "40ms"
    }
  ]
}
```

### 工作方式

smart 出站为**每个目标**单独选择线路，而不是全局选一条。

一条代理链路分为三段：**local** 是本地到**最内层**代理的耗时（含中转链内部的每一跳），**remote** 是最内层代理到目标的耗时。naive 协议扩展让代理在 CONNECT 响应里回报它拨号目标所花的时间，于是这两段可以分别测量。存在代理链时，local 覆盖到最内层代理为止的所有跳，remote 始终是最后一跳到目标的耗时。

这个拆分很关键，因为两段的性质完全不同：local 是**节点属性**，跨目标基本恒定；remote 是**目标属性**，对 CDN 与 anycast 地址会塌缩到 1ms 左右。

选择按下式排序，取最小值：

```
score = alpha × local + remote − bonus
```

首次访问某个目标时，会同时向所有分组发起一次 CONNECT 探测并比较结果。探测不携带任何数据，因此目标只会看到每个分组出口各来一次连接尝试，别的什么都没有。结果写入磁盘缓存，之后的连接直接使用缓存，不再探测。

目标是域名时，出口需要现做域名解析的那些分组，会在这一轮结束之后被再问一次，用第二次的读数替换第一次。原因是解析耗时不是路径的属性：已经承载该目标的分组，它的出口缓存里有这个名字，其它分组没有——于是每次复测都会把在位组测成暖的、把挑战者测成冷的，把一个劣势冻进本来用于纠正劣势的那一轮。代价是这些分组多发一次同样不携带数据的连接，与第一次相隔不到一秒、来自同一个出口；出口已经有这个名字的分组不会被再问，而一个目标被比较过之后这才是常态。

触发比较的那条连接不会为完整结论买单：一旦继续等待已经无法改变**它自己**能拿到什么，它就带着当前最优的隧道离开。还没答复的分组会在后台再收一小段宽限 —— 答复到达时间里含有代理自身的 DNS 耗时，而首次访问恰恰是 DNS 最冷的时刻 —— 结论由所有交出答复的分组共同写成。若完整结论指向另一个胜者，该目标的下一条连接就会用它。

!!! note ""

    只有 naive 类型的出站可以放进 smart 分组：排序依赖的目标拨号耗时只有 naive 会回报。

### 中转链怎么算

存在中转时，`local` 覆盖到最内层代理为止的所有跳，包括「中转→出口」这一段。这一段既不属于本地接入，也不属于目标距离，但它会实实在在地拖慢每一条连接。

三段可以从协议里直接算出来，不需要额外字段：

```
near  = 客户端测的往返 − 第一跳自报的耗时      客户端 → 中转
chain = 第一跳自报的耗时 − 最内层的拨号耗时     中转 → 出口（多级链则是全部中间跳）
remote= 最内层的拨号耗时                       出口 → 目标

near + chain + remote = 往返
```

`local = near + chain`。直连节点的 chain 就是它自己的路由开销，实测不到一毫秒，所以直连的排序几乎不受影响；而一个中转，只要「中转→出口」变坏，`local` 就会跟着涨，分组会照常换到更好的成员。

最内层那一跳还会另外上报「这次里有多少是**找到**目标、而不是**连上**目标」，客户端把这部分算进 `remote`。不上报的话，出口的一次冷域名解析就会掉进 `chain`——那是每个目标各自的开销，却记在了节点头上，一次赶上几条就足以把分组从一个表现完全正常的成员上挪走。之所以是**挪进 `remote`** 而不是直接扣掉：一是三段之和还要恒等于往返，二是客户端从头到尾只用「拨号耗时 + 解析耗时」这个和，于是上报这个字段并没有给任何一跳新的可撒谎空间。出口版本太旧、不上报这个字段时，解析耗时仍然留在 `chain` 里，和以前一样。

估计量按各段的性质选：near 取最近若干次的**最小值**（干扰它的排队与冷握手只会把样本推高，取下界最稳）；chain 取**去掉单个最差样本后的均值**（要估的是代价而不是能力——一条丢四分之一包的链路，它「最好能做到多快」和完好时一模一样，取最小值等于看不见）。

### 节点的死活怎么判

空闲的节点会被定期探测，探测目标取决于这个节点被测出来是什么。

**没有链内段**的节点——也就是自己拨号去目标的节点，单跳部署里的每一个节点都是——探测目标是一个由**服务端自己应答、不向外拨号**的地址。什么都不会离开代理，所以探测可以随便跑，回来的往返也就纯粹是「本地到代理」那一段，正好是排序需要的量。对这类节点，下游看到的东西和以前逐字相同。

有链内段的节点——也就是**中转**——探测改用真实地址，因为有两件事没有别的办法能问出来：这段链内此刻要花多少，以及它还在不在。一个自身活着、上游却断了的中转，照样能完美应答那个自答地址（它压根不拨号），于是心跳一直说它健康，而它拒绝着每一个真实目标。实测遇到过：真实流量在失败的同一秒，心跳返回 128ms，节点从未被判死。

当一次真实拨号失败、需要**确认**节点死活时，以及一个已经被判死的节点要求**重新启用**时，用的是同样这批真实地址。

真实地址有两个（`1.1.1.1:443` 与 `9.9.9.9:443`），分属不同运营方。单靠一个地址扛不住判死这个结论：出口对某个特定地址做的事，它每一轮都会做一遍，所以只按一个地址判的节点，要么整个进程生命周期里被永久判死，要么永远判不死，两者都不是关于这个节点的读数。一个被拒或被丢弃、另一个应答，是关于那个地址的结论；两个都失败，才是关于出口的结论。两个都用 IP 字面量，是为了让代理侧坏掉的解析器无法把结论带偏；两个都是 anycast，所以离出口本身很近。

唯一**不**做交叉验证的，是代理明确回答「我自己的下一跳没了」。那是它关于自身的陈述，换任何目标都绕不开那一段，再问一次只会拖延结论。除此之外——地址被拒、超时、地址被静默丢弃——都会先问第二个地址。

真实流量本身就在测量繁忙的中转，而最近承载过流量的节点会被心跳整轮跳过——所以这类探测只会由闲置的中转发出，而那恰好是状态最无从得知的那一批。

### 排序信任谁

两个测量量都来自服务端。local 是本地测得的往返减去服务端自报的自身耗时，remote 是服务端自报的目标拨号耗时。也就是说，一个把自身耗时报成整个往返、把连接耗时报成 0 的服务端，会把自己描述成既紧贴客户端又紧贴每一个目标，从而赢下它参与的每一次比较。

有两道收紧：

- 与本地测量对不上的上报会被整份丢弃 —— 自身耗时不可能超过包住它的往返，连接耗时也不可能超过包住它的自身耗时。
- TLS 握手是在客户端这一侧、在服务端开口之前测的。一个节点不能声称自己比它自己的握手所允许的还要近。

剩下的是一条真实存在的信任边界：节点仍然可以在这两道界限之内低报自己的距离，客户端分辨不出来。把你不愿意交出路由决策权的节点单独放一个分组、给你信任的分组配 `bonus`，或者干脆不要放进 smart。

这条边界内部还有一个不对称，用 `select: fastest` 时值得知道。**分组之间**比较时，把目标段报大是吃亏的——分数里直接算它的账。但**同一分组的成员之间**只比 `local`，把目标段报大会让这个成员自己的链内段等量变小，于是在组内反而占便宜。它靠这个能抢到的上限就是它真实的链内段，而且同一份报大会让整个分组在组间显得更差；但如果一个分组里的成员并非同等可信，`first` 根本不提供这个杠杆。

### 决策存在哪里

比较结果会写进 sing-box 的缓存文件，这样重启后不必重新比较每一个目标 —— 也就不会在重新比较的这段时间里把流量送去另一个国家。需要开启 `experimental.cache_file`；没有它每次重启都从零开始。

每个分组的 remote 会保留**最近数次比较的读数**：攒够三次以后取其中位数，不足三次时就用最新的那一次。anycast 目标本来就会在两次比较之间给出完全不同的答案 —— 同一个代理这一轮拨到 0.5ms、下一轮 150ms —— 只看最后一个读数意味着某一轮的运气会被冻结整个快照寿命：一个分组靠一次走运的读数胜出，之后每条连接都失望；或者被一次倒霉的读数淘汰，白白坐冷板凳好几个小时。攒够样本以后，孤立的一轮会被周围的历史否决，而真正的变化 —— 一轮接一轮地出现 —— 很快就会成为多数。

两个读数不构成中位数：取其中较小的那个等于永远相信更好看的那次，还要把它多留一轮，这和保留历史的初衷正好相反。所以在够到三个读数之前，最新的那次测量就是最好的估计。

### 快照什么时候重新验证

快照会因为**变旧**或者**被用得太多**而重新比较，两者都在后台进行，旧结论在新结论出来之前继续服务。

按时间过期只解决了一半问题。没被选中的分组只有在重新比较时才会被重新测量，所以无论一份快照承载了多少流量，它那些落选的测量值永远和写下它的那一轮一样老。实测遇到过：一个每 26 秒轮询一次的定位服务，靠着一个离群读数把某个出口排除了将近五个小时 —— 789 次请求，每次多付约 155ms，而那个出口早就恢复了，却没有任何机制会去看它一眼。因此快照每服务满一定数量的请求也会重新验证：一次比较的成本是每个分组一次拨号；目标是域名时，出口需要现解析的那些分组各再加一次重测——复测时那就是除在位组以外的每一个组。摊到上百次请求上仍然只占其中几个百分点。闲置的目标碰不到这个上限，仍然只按时间过期；繁忙的目标则把自己流量中的一小部分用来保证结论仍然诚实。

此外，正在使用的分组如果连续多次实测都远差于快照记录，会立即触发重新比较，并且这几次实测会被计入该分组的 remote 历史。实测通常不进快照 —— 只有被选中的分组有流量，拿它自己的热数据给它加分会让它永远待在原位 —— 确认过的劣化是唯一的例外：它只可能让这个分组看起来更差，不可能更好。

快照里还记着当时是**哪个成员**代表每个分组参加的比较，没答复的那些分组也记。一个分组失去它的节点有两种情形，处理方式正好相反：

- **节点坏了、分组落到备用上** —— 快照描述的还是它马上就要回去的那个节点，此刻重新比较只会把好的测量值换成故障期间测出来的，而且是在该分组碰过的每一个目标上、在故障本身已经在制造负载的时刻。不动。
- **节点回来了，或者另一个成员测得更好，分组离开了备用** —— 快照描述的是那个备用：一个答得慢、或者干脆没在预算内答复的替补。这个结论从来就不是关于现在这个分组的，而且没有别的办法发现，因为一个始终没答复的分组不留下任何测量值。这种目标会在下次拨号时重新比较。

区分二者的依据是当时参赛的那个节点现在是否健康。这样"某个节点抖了五分钟"的影响范围就收敛回那五分钟，而不是按快照寿命一直留着。

目标以摘要而非原文存储，因此这个文件不会成为一份可读的浏览历史。摘要没有加盐 —— 任何盐都得存在同一个文件里 —— 所以同时拿到文件**和**一份候选域名清单的人，仍然可以逐一验证哪些出现在里面。超过一周没有刷新过的快照会在启动时清掉。

### 字段

#### alpha

==默认: 0.7==

对 local 段的折扣系数，取值 0 到 1。

`1.0` 表示纯粹按总耗时排序。小于 1 时，总耗时接近的情况下会偏向 remote 更短的节点 —— 适用于本地到代理带宽有保障、更在意代理到目标那一段的场景。`0` 表示只按 remote 排序。

这是一个连续量而非阈值：阈值会在边界附近来回翻转，导致同一个站点的出口地址反复变化。

#### audit_path

==默认: 关闭==

把每一次路由决策以及支撑它的测量值持久记录到这个文件，每行一个 JSON 对象。

日志替代不了它。一条路由选错通常要几小时后才被发现，那时能解释它的 journal 早被轮转掉了；而且残存的信息散在几十行里，需要人工拼接。这个文件是一行一决策，每行自包含：

| `type` | 何时写入 |
|---|---|
| `race` | 一轮探测决定了一个目标。带上每个分组的两段耗时、bonus、静态下界和分数 |
| `switch` | 某个目标所走的分组发生了变化。带上变化前后以及促成变化的数值 |
| `member` | 某个分组所用的成员发生了变化 —— 同样改变了出口地址，但没有任何目标换组 |
| `state` | 某个目标当前被记住的状态。整张表每小时写一次，关闭时再写一次 |
| `usage` | 每个节点在过去十分钟里承载了多少请求、是什么把流量送过去的，以及这些请求分别落在哪些目标上 |
| `amend` | 某个目标的读数在出口拿到域名之后被重测，带上它替换掉的那个值，以及使这次重测值得做的那段解析耗时 |

计数是**每个窗口的增量**而不是累计值：重启会把计数器清零，而跨天的记录里重启几乎必然发生。窗口可以相加得到总量，累计值不能。

读回来：

```
sing-box smart nodes /var/lib/sing-box/smart-audit.jsonl [--list] [--top N]
```

按节点输出承载的请求数与当前持有的目标数；加 `--list` 时逐个列出这些目标各自承载了多少请求，按请求数从多到少，`--top N` 只看前 N 个。

请求数覆盖文件里的所有窗口，目标列表来自最近一次整表转储 —— 两个范围都打在开头。因此一个节点的总数可能大于列出来的那些之和：差额是已经不在表里的目标承载的，会单独列一行说明，不会悄悄对不上。

!!! warning ""

    这是唯一会把目标域名明文落盘的地方，快照缓存刻意只存摘要。打开它等于用这一点隐私换取"能把路由和现实对账"的能力。

#### audit_size

==默认: `64MB`==

文件增长到多大时轮转，保留一份上一代 —— 所以磁盘占用是这个值的两倍，不会更多。

#### groups

分组列表。一个分组表示**你认为这些节点到同一目标的 remote 耗时相同** —— 通常意味着它们共用同一片出口网络。

同一分组只探测一次、只保存一份 remote 测量值，组内成员之间也不会互相比较排序。如果两个节点的出口 IP 段不同、到目标的路径也不同，应当配置成两个分组。

#### groups.tag

分组名称，必填。

#### groups.outbounds

该分组的出站标签列表，必须都是 naive 类型。

#### groups.select

==默认: `first`==

组内成员的选择方式：

| 值 | 行为 |
|---|---|
| `first` | 按配置顺序使用第一个健康成员，仅在故障时顺延，恢复后切回 |
| `fastest` | 使用 local 最小的健康成员 |

任何时刻只使用一个成员，不做轮转 —— 同一目标的两次连接从不同地址发出，会破坏登录态并触发风控。

#### groups.bonus

==默认: `0`==

愿意为使用该分组额外付出的耗时。

延迟无法测量"出口地址是否干净"，这一项由你来声明。它在 remote 很小时（CDN、anycast，各节点 remote 都是一两毫秒）决定胜负，在 remote 很大时被淹没 —— 因此不需要任何"是否 CDN"的判断逻辑。

数值可以直接推算：若节点 A 的 local 为 29ms、节点 B 为 80ms，`alpha` 为 0.7，则 B 需要 `0.7 × (80 − 29) ≈ 36ms` 的 bonus 才能在 remote 相当时胜出。
